01 — Abstract

Public ML repositories are how industry teams decide whether a method is worth adopting. Running them is rarely a clone-and-execute exercise, and it gets harder when the code assumes CUDA and the machine in front of you is an AMD GPU.

Repo2ROCm takes a repository URL and migrates that CUDA-centric codebase onto ROCm with no manual steps. It rebuilds the environment, adapts device assumptions and custom kernels, runs a real workload, and accepts success only when runtime evidence shows the workload executed on the AMD GPU. Installation, an import, or a --help screen is not enough.

We evaluate on ResearchBench, 60 repositories from recent ICLR, ICML, ACL, and NeurIPS papers. Eighteen run out of the box. Repo2ROCm verifies functional reproduction for 59. Against general-purpose coding agents that share the same Claude Sonnet 4 backbone, it also preserves the accelerator path more faithfully.

A repository that runs only after disabling FlashAttention, falling back to CPU, or shrinking the workload is no longer the experiment in the paper.

02 — System

Plan outside Docker. Execute behind hard guards.

A GitHub URL goes in. A verified AMD-GPU run comes out, with a Dockerfile, a source patch, command logs, verification evidence, and the full agent trajectory.

03 — Method

Evidence-gated migration, in three modes.

Mode What it asks Outcome
Mode 0 Clone and follow the repository’s own instructions. No agent. 18/60
Mode 1 Functional reproduction. Real workload, on the AMD GPU, with the accelerator path intact. 59/60
Mode 2 After Mode 1, compare measured metrics with the paper’s targets and tolerances. 1 of 2 cases
Planning · outside Docker

Fingerprint, then one plan.

  1. Clone the repository and detect frameworks, dependency files, entry points, CUDA packages, and custom .cu kernels.
  2. Rank candidate ROCm base images. Package overlap is a Jaccard score over normalized dependency tokens, with filters for architecture, GPU family, and images that have already failed.
  3. Emit a single plan: install path, migration hazards, workload command, and validation checks. Mode 2 also records a metric and a tolerance when both are unambiguous.
Execution · inside the sandbox

One action, then proof.

  1. A ReAct executor follows the plan one action at a time in a GPU-pinned container. Successful milestones are checkpointed; failures roll back.
  2. Custom CUDA extensions go through a kernel agent: CUDA-to-HIP conversion, including hipify, then a build-and-load check.
  3. Hard guards block an image switch, an accelerator-library swap, a critical source edit, or a success claim until deterministic tools supply runtime evidence.

A run counts only if all four hold.

  1. 01An official workload finishes: inference, training, evaluation, or a forward pass.
  2. 02Runtime evidence shows that workload ran on AMD hardware through ROCm.
  3. 03Accelerator-critical pieces stay in place. Attention backends, custom kernels, and GPU libraries are not disabled, stubbed, or swapped for a degraded path such as SDPA in place of FlashAttention.
  4. 04No unreported CPU fallback, backend substitution, disabled module, or toy-scale run.

The language model cannot override that verdict. An observer sidecar breaks repeated failure loops, and causal memory offers hints from earlier repositories. Distilled hints never bypass the guards.

04 — Results

ResearchBench, on eight MI350X GPUs.

The misses out of the box are the usual research-code failures plus ROCm-specific ones: CUDA-only dependencies, the wrong container, hard-coded CUDA checks, silent CPU fallback, stale APIs, and small source bugs. The single Mode 1 miss, DiffusionVeteran, also fails out of the box. It is not a regression from a working baseline.

Host: eight AMD Instinct MI350X GPUs (gfx950, 270.6 GB HBM3E), ROCm Runtime 1.18. Backbone: Claude Sonnet 4, capped at 100 turns. A typical run uses about 719K tokens (median 608K) and 18–20 minutes. Repeating three repositories five times each, all 15 of 15 runs matched the original verification outcome.

Same model. Higher fidelity.

Binary “it ran” is too coarse. Agents often get a green run by replacing FlashAttention with SDPA, disabling a GPU module, or shrinking the workload. The Portability Fidelity Score charges for that. On a ten-repository diagnostic set chosen before any scores were known, every agent used Claude Sonnet 4, the same revision, hardware, budget, and public ROCm docs.

Ran is 1 only when the run produced runnable evidence. Path fidelity grades each accelerator-critical component as preserved, degraded, or disabled. The ordering holds under equal component weights and when any single component is removed. This comparison is diagnostic, not a score over all 60 repositories.

Mode 2 is a case study, not the main claim.

Paper result reproduced

TurboQuant

After a verified ROCm environment, the quantization command’s compression, similarity, and match rate all landed inside the stated tolerance.

Not reproduced

dKV-Cache

Mode 1 succeeded: the intended workload ran on AMD GPUs. The reported hardware-sensitive speedup did not fall within tolerance, so Mode 2 refused the claim.

One of two preliminary cases matched. Missing datasets, gated checkpoints, and incomplete evaluation scripts still block result-level checks even when the code runs. Causal memory, ablated on 20 GPU-dependent repositories, moved the functional-run rate from 15/20 to 18/20 and gave a 1.16× speedup on repositories both settings finished.

05 — What every run ships

An audit bundle, not a chat log.

Dockerfile
The ROCm environment the planner selected and the executor built.
Unified diff
Source changes against the original repository, including kernel ports.
Command logs
What ran inside the sandbox and what ran outside it.
Verification
ROCM_ENV_VERIFIED, or a Mode 2 metric report with a match or a mismatch.
Plan and trajectory
The static plan and the step-by-step agent trace used for audit and distillation.
Code
System, benchmark artifacts, and reproduction instructions on GitHub.
